## 1. 产品定位与目标

### 1.1 产品定位

**DataForge 造数工厂**是一款面向测试/开发团队的自动化测试数据生成平台。

核心解决以下痛点：

| 痛点 | DataForge 解法 |
|------|----------------|
| 手动造数耗时、易出错 | 可视化配置字段策略，一键批量生成 |
| 跨表关联数据难以维护 | 字段关联机制，级联一致性插入 |
| 千万级造数慢、失败无保障 | 多线程批量插入 + 重试 + 断点续传 |
| 造数经验无法复用 | Case 管理，沉淀可复用的造数模板 |
| 多 Case 依赖顺序难以手动协调 | 场景管理，可视化编排多 Case 串并行执行 |
| 团队数据互相干扰 | 分组数据权限隔离 |
| 常用数据（身份证等）生成繁琐 | 内置快捷工具箱 |

### 1.2 产品目标（一期）

- 支持 MySQL 数据源的可视化造数配置与执行
- 支持千万级别数据量的高性能批量插入
- 完善的 Case 管理和执行历史追踪
- **场景管理：将多个 Case 编排为有序执行流程，支持串行/并行/条件跳过**
- 分组数据权限隔离（销项组 / 申报组）
- 内置常用造数工具箱
- 预留 AI 调用接口，为二期 AI 智能造数铺路

### 1.3 设计风格要求

- **整体风格**：简洁高级，参考 Kiro 官网设计语言
  - 深色背景（#0d0d0d / #111827）为主基调
  - 渐变高亮边框卡片（紫色/蓝色渐变）
  - 玻璃态（glassmorphism）组件效果
  - 字体：中文用苹方/思源黑体，英文用 Inter
- **装饰元素**：线条猫咪（Lineart Cat）作为全站吉祥物
  - 登录页：大尺寸猫咪插画
  - 侧边栏底部：小猫咪坐姿图标
  - 加载状态：猫咪行走动画
  - 空状态页：猫咪睡觉插画 + "暂无数据，小猫在打盹～"
  - 执行成功：猫咪竖大拇指庆祝动效

#### 1.4.2 页面级 loading 与空状态规范

**Loading 状态：**

| 场景 | 呈现方式 |
|------|---------|
| 页面首次加载（列表/详情） | 骨架屏（Skeleton），与实际内容布局一致 |
| 表格数据刷新（筛选/翻页） | 表格内容区 spin 遮罩（半透明，不影响筛选栏操作） |
| 按钮触发的操作（保存/执行） | 按钮自身 loading 状态（禁用 + 转圈图标），不全屏遮罩 |
| 文件导出/大批量生成（>1000条） | 进度条展示，见各工具章节 |

**空状态：**

| 场景 | 呈现方式 |
|------|---------|
| 列表无数据（首次使用） | 猫咪睡觉插画 + 引导文案（如「还没有 Case，去造数引擎创建第一个吧 →」）+ 操作按钮 |
| 列表无数据（筛选后为空） | 猫咪睡觉插画 + 「没有符合条件的数据，小猫在打盹～」+ 清空筛选按钮 |
| 图表无数据 | 图表区域显示「暂无数据」文字，不渲染空坐标轴 |

**请求失败状态：**

| 场景 | 呈现方式 |
|------|---------|
| 列表/详情接口失败 | 页面内容区显示错误占位：「加载失败，请稍后重试 [🔄 重试]」 |
| 按钮操作失败 | Naive UI Message 组件顶部弹出红色提示（3 秒自动消失） |
| 网络断开 | 顶部通知条显示「网络连接已断开，部分功能不可用」（黄色，可关闭） |

#### 1.4.3 登录态超时处理规范

JWT Token 有效期 7 天，超时后前端请求会收到 `1001` 错误码，处理策略如下：

**超时感知方式：** 前端不主动轮询 Token 状态，通过接口响应的 `1001` 错误码被动感知。

**处理行为：**

| 场景 | 行为 |
|------|------|
| 普通页面操作（点击按钮、切换菜单）触发接口返回 1001 | 弹出「登录已过期」Modal（非全页跳转），用户可在 Modal 内直接输入密码重新登录，登录成功后 Modal 关闭，**原页面状态保留**（表单数据、筛选条件不丢失） |
| 页面加载时（进入路由）接口返回 1001 | 直接跳转登录页（页面尚未有用户操作，无需保留状态） |
| 正在执行造数任务期间 Token 过期 | 任务继续在后台执行（Celery 异步，不依赖前端 Token）；前端轮询进度接口收到 1001 时弹出重登 Modal；重登成功后自动恢复轮询 |

**重登 Modal 设计：**

```
┌────────────────────────────────────┐
│  🔒 登录已过期                      │
│  ──────────────────────────────    │
│  当前账号（popsicle）的登录已过期，  │
│  请重新输入密码以继续操作。           │
│                                    │
│  密码  [____________________]      │
│                                    │
│  [取消并跳转登录页]  [重新登录]      │
└────────────────────────────────────┘
```

- 用户名只读（显示当前账号），只需输入密码
- 「取消并跳转登录页」：清除本地 Token，跳转 `/login`，当前页面操作丢失
- 重登成功后：更新本地 Token，关闭 Modal，**自动重试触发超时的那次请求**

### 2.3 菜单权限体系

菜单权限粒度设计如下，管理员可按用户勾选授权：

### 2.4 数据权限隔离规则

| 角色 | 可见数据范围 |
|------|-------------|
| `ADMIN` | 全量数据（所有分组） |
| `GROUP_SALES` | 仅 `group_type = 1`（销项组）的数据 |
| `GROUP_DECLARE` | 仅 `group_type = 2`（申报组）的数据 |

**隔离实现方式：** 后端所有查询接口自动注入 `group_type` 过滤条件，前端无法绕过。涉及数据：
- 造数 Case
- 执行任务记录
- 数据源（数据源本身也按组隔离，不同组不能互见）
- 造数总览统计数据

#### 4.4.3-A 字段默认策略自动推断规则

用户进入字段配置页时，系统根据字段元数据**自动预填**最合理的造数策略，减少手动配置量。推断优先级从高到低依次匹配：

| 优先级 | 匹配条件 | 自动推断策略 | 说明 |
|--------|---------|------------|------|
| 1 | 主键 + `extra = AUTO_INCREMENT` | **SKIP（跳过）** | DB 自动填充，无需造数，行显示灰色禁用 |
| 2 | 主键 + `data_type IN (bigint, int)` + 非自增 | `SNOWFLAKE` | 整型主键优先用雪花 ID |
| 3 | 主键 + `data_type IN (varchar, char)` | `UUID` | 字符串主键用 UUID v4 |
| 4 | 唯一索引字段 + `data_type IN (int, bigint)` | `INCR_FROM`（起始值=1） | 数字唯一索引自增保证不重复 |
| 5 | 唯一索引字段 + `data_type IN (varchar, char)` | `UUID` | 字符串唯一索引用 UUID |
| 6 | 字段名匹配 `created_at / create_time / created_time` | `NOW` | 创建时间字段 |
| 7 | 字段名匹配 `updated_at / update_time / updated_time` | `NOW` | 更新时间字段 |
| 8 | 字段名匹配 `deleted_at / delete_time` | `CUSTOM_VALUE`（值=NULL） | 逻辑删除时间，默认 NULL |
| 9 | 字段名匹配 `is_deleted / is_del / del_flag` | `CUSTOM_VALUE`（值=0） | 逻辑删除标记，默认未删除 |
| 10 | 字段名包含 `phone / mobile / tel` + `char_max_length IN (11,13)` | `RANDOM_FIXED_LEN`（位数=11） | 手机号字段 |
| 11 | 字段名包含 `id_card / identity / id_no` + `char_max_length = 18` | `RANDOM_FIXED_LEN`（位数=18） | 身份证字段 |
| 12 | 字段名包含 `status / state / type / flag` + `data_type = tinyint` | `PICK_FROM_LIST`（预填 0 / 1） | 枚举状态字段 |
| 13 | `data_type IN (datetime, timestamp)` | `NOW` | 其他时间类字段 |
| 14 | `data_type = date` | `NOW` | 日期字段 |
| 15 | `column_default IS NOT NULL` | `CUSTOM_VALUE`（值=column_default） | 有默认值的字段直接使用默认值 |
| 16 | 其他字段 | `DEFAULT`（随机） | 通用兜底 |

**SKIP 策略说明：**

- `AUTO_INCREMENT` 主键行在配置表中显示为灰色行，策略列展示「⚙️ 数据库自动填充」标签，不可修改
- 关联管理中不能将 SKIP 字段设为关联目标（自增值在执行前未知，无法预先设定）
- 执行时 SKIP 字段完全不出现在 INSERT 语句的列列表中

#### 4.4.3-B AUTO_INCREMENT 主键完整处理规范

`AUTO_INCREMENT` 是 MySQL 中最常见的主键模式，需要明确处理边界：

**识别条件：** `df_column_cache.extra` 字段包含 `auto_increment`

**处理规则：**

| 场景 | 处理方式 |
|------|---------|
| 单列自增主键 | 自动 SKIP，INSERT 语句不包含该列，由 MySQL 自动赋值 |
| 联合主键（含自增列） | 自增列 SKIP，其他主键列按各自类型配置策略 |
| `INCR_FROM` 起始值与自增序列冲突 | 执行前检查目标表当前 AUTO_INCREMENT 值，若用户指定的起始值 < 当前自增值，给出警告提示 |
| 唯一索引中含自增列 | 自增列已 SKIP，唯一性由 MySQL 自增保证，无需额外处理 |

**执行时的自增值冲突预检（在执行弹窗中展示）：**

```
⚠️ 检测到主键 id 为 AUTO_INCREMENT，造数时将由数据库自动填充。
   当前表的 AUTO_INCREMENT 值为：10,542
   本次造数完成后，AUTO_INCREMENT 将推进至约：10,542 + N
```

#### 4.4.4 造数策略详细说明

**通用字符/数字字段策略选项：**

| 选项值 | 显示名称 | 策略参数控件 | 校验规则 |
|--------|----------|-------------|----------|
| `DEFAULT` | Default（随机） | 无 | — |
| `RANDOM_FIXED_LEN` | 随机 X 位生成 | 数字输入框（位数 X） | X ≤ 字段最大长度，X ≥ 1 |
| `RANDOM_RANGE_LEN` | 随机 X~Y 位生成 | 两个数字输入框（X 和 Y） | 1 ≤ X < Y ≤ 字段最大长度 |
| `CUSTOM_VALUE` | 自定义输入 | 长文本输入框 | 输入值与字段类型兼容（见校验规则表） |
| `PICK_FROM_LIST` | 从列表随机选取 | 多行文本域（换行分隔每个值） | 非空，每个值不超字段最大长度 |
| `ITERATE_LIST` | **按序遍历插入** | 多行文本域（换行分隔每个值）+ 每值插入条数输入框 | 非空，每个值不超字段最大长度，条数 ≥ 1 |

> **`ITERATE_LIST` 策略说明（重要）：**
> 区别于随机选取（每条数据独立随机选一个值），**按序遍历插入**是一种「驱动型」策略：
> - 执行时以该字段的 value list 为驱动，**逐值循环**，每个 value 触发一轮完整插入
> - 每轮插入：该字段固定为当前 value，主表插入「每值条数」行；所有关联字段对应的表也各插入相同数量的行，且关联字段值与当前 value 保持一致
> - 最终总条数 = list 长度 × 每值条数（每张涉及表均如此）
> - 一个 Case 中**最多只能有一个字段**使用 `ITERATE_LIST` 策略（因为多个驱动字段会产生笛卡尔积爆炸，不合理）
> - 若同时配置了其他字段的关联，关联字段在每轮中也以当前 value 填充
>
> **举例：** 表 A 字段 a 设置 `ITERATE_LIST`，list=["qwer","asdf","zxcv"]，每值插入 10 条，并关联了表 B.b 和表 C.c：
> - 第 1 轮：A 表插入 10 行（a="qwer"），B 表插入 10 行（b="qwer"），C 表插入 10 行（c="qwer"）
> - 第 2 轮：A 表插入 10 行（a="asdf"），B 表插入 10 行（b="asdf"），C 表插入 10 行（c="asdf"）
> - 第 3 轮：A 表插入 10 行（a="zxcv"），B 表插入 10 行（b="zxcv"），C 表插入 10 行（c="zxcv"）
> - 最终：每张表各 30 行，3 张表共 90 行

**主键 / 唯一索引字段策略选项（替代通用选项）：**

| 选项值 | 显示名称 | 策略参数控件 | 说明 |
|--------|----------|-------------|------|
| `UUID` | 随机 UUID（默认） | 无 | 生成 UUID v4，去掉连字符或保留可配 |
| `SNOWFLAKE` | 雪花 ID | 无 | 基于时间戳生成，适合 bigint 主键 |
| `INCR_FROM` | 指定值自增 | 起始值输入框（正整数） | 多线程用 Redis 原子计数器保证唯一 |

**时间类字段策略选项：**

| 选项值 | 显示名称 | 策略参数控件 | 说明 |
|--------|----------|-------------|------|
| `NOW` | 当前时间（默认） | 无 | 执行时插入 `NOW()` |
| `RANDOM_TIME_RANGE` | 随机时间段 | 时间范围选择器（起始~结束） | 在范围内均匀随机 |
| `FIXED_TIME` | 固定时间 | 时间选择器 | 所有行插入相同时间 |

**布尔/枚举类字段策略：**

| 选项值 | 显示名称 | 策略参数控件 |
|--------|----------|-------------|
| `DEFAULT` | 随机 0/1 | 无 |

#### 4.4.6 关联管理抽屉

**打开方式：** 点击顶部【关联管理】按钮，右侧滑出抽屉

**功能说明：**

1. 选中一个字段后，点击【添加关联】
2. 弹出关联配置弹窗：
   - 当前字段：显示表名 + 字段名 + 类型（只读）
   - 目标表：下拉选择当前数据源下的所有表
   - 目标字段：选定目标表后下拉展示兼容类型的字段
   - 点击确认添加

   - 格式：`源字段名` → `目标表名.目标字段名`

4. 一个字段可关联多个目标字段（多条记录）

**关联语义：** 执行造数时，源字段与所有关联目标字段插入完全相同的值（保证外键一致性）。

**关联约束：**
- 不允许循环关联（A→B，B→A）
- 不允许自关联（表内同字段）
- 目标字段类型须与源字段类型兼容（varchar↔varchar，int↔bigint 等）

### 4.5 造数执行引擎核心逻辑

#### 4.5.1 执行流程

```
用户触发执行
    │
    ▼
① 参数验证（case 配置合法性、数据源连通性）
    │
    ▼
② 创建 df_exec_task 记录，status=待执行
   生成 task_no（雪花 ID）
    │
    ▼
③ 提交到异步任务队列（Celery），立即返回 task_no 给前端
    │
    ▼
④ Celery Worker 接收任务：
   a. 分析关联关系，构建插入依赖图（拓扑排序）
   b. 确定插入顺序（有关联的表按依赖顺序）
   c. 计算每批次大小（默认 1000 条/批，大任务可配置 5000）
   d. 初始化自增计数器到 Redis（INCR_FROM 策略）
    │
    ▼
⑤ 多线程并行执行（ThreadPoolExecutor）
   每个线程负责一批数据的生成+插入：
   a. 生成批次数据（Python 本地生成，不依赖 DB）
   b. 构建 bulk INSERT SQL（VALUES 批量拼接）
   c. 执行 INSERT，记录 df_exec_batch_log
   d. 成功则更新 Redis 进度计数器
    │
    ▼
⑥ 全部完成后：
   a. 更新 df_exec_task.status = 成功/失败/部分成功
   b. 清理 Redis 自增计数器
   c. 触发执行完成通知
```

#### 4.5.1-B ITERATE_LIST 遍历模式执行流程

当 Case 包含 `ITERATE_LIST` 策略字段时，执行器切换为**遍历驱动模式**，流程如下：

```
解析 config：识别到 ITERATE_LIST 驱动字段（如 A.a）
    │
    ▼
确定遍历参数：
  drive_values   = ["qwer", "asdf", "zxcv"]   （list 中全部值）
  rows_per_value = 10                          （每值插入条数）
  total_rounds   = 3                           （= len(drive_values)）
    │
    ▼
逐轮串行执行（Round 1 → Round 2 → Round 3）：
    │
    ├── Round 1：drive_value = "qwer"
    │       ├── 固定 A.a = "qwer"，按各自策略生成 10 行 A 表数据
    │       ├── 固定 B.b = "qwer"，生成 10 行 B 表数据
    │       ├── 固定 C.c = "qwer"，生成 10 行 C 表数据
    │       └── 同轮内无依赖的表多线程并行插入，记录进度
    │
    ├── Round 2：drive_value = "asdf"  （同上）
    └── Round 3：drive_value = "zxcv"  （同上）
    │
    ▼
汇总：每张表 30 行，3 张表共 90 行
```

**进度面板在遍历模式下的额外展示：**
- 总进度条改为「已完成轮次 / 总轮次」（如「2 / 3 轮」），下方附当前整体条数进度
- 分表区额外展示当前轮正在使用的 drive_value（如「当前值：asdf」）
- 预计剩余时间基于「平均每轮耗时 × 剩余轮数」估算

**遍历模式的失败与重试：**
- 单轮内批次失败沿用批次级重试（最多 3 次，指数退避）
- 某轮整体失败 → 记录该轮失败，**继续后续轮次**，不中止整体任务
- 最终：全轮成功=成功 / 部分轮失败=部分成功 / 全轮失败=失败
- 执行详情页支持「重试失败轮次」（选中失败轮，单独重跑）

#### 4.5.2 失败重试机制

- **单批次失败：** 立即原地重试 3 次（指数退避：1s → 2s → 4s）
- **3次重试仍失败：** 记录 batch_log.status=失败，跳过当前批次继续后续批次
- **整体任务失败（失败率 > 50%）：** 任务状态置为失败，停止执行
- **整体任务部分失败（失败率 ≤ 50%）：** 任务状态置为部分成功
- **手动重新执行：** 在执行记录详情页点击「重试失败批次」，仅重试失败的批次（断点续传）

#### 4.5.3 数据生成策略实现

| 字段类型 | DEFAULT 策略生成规则 |
|----------|---------------------|
| varchar(N) | 随机字母数字字符串，长度 min(10, N) |
| int | random.randint(1, 2147483647) |
| bigint | random.randint(1, 9223372036854775807) |
| decimal(M,D) | 随机生成符合精度的小数 |
| datetime/timestamp | 当前时间 datetime.now() |
| date | 当前日期 date.today() |
| tinyint(1) / bool | random.choice([0, 1]) |
| text/longtext | 随机 100~500 字符的 Lorem 文本 |
| char(N) | 固定 N 位随机字符串 |

### 5.5 Case 版本管理边界说明

**一期版本策略：覆盖式更新，不做版本管理。**

| 行为 | 说明 |
|------|------|
| 修改 Case | 覆盖 `config_json`，无历史版本记录 |
| 历史执行快照 | 每次执行时将 `config_json` 完整快照存入 `df_exec_task.case_snapshot`，执行记录永久保留执行时的配置状态 |
| 查看历史执行时的配置 | 在执行详情抽屉中展示 `case_snapshot`，标注「执行时配置（可能与当前 Case 配置不同）」 |
| 配置对比 | 一期不提供当前配置 vs 执行时配置的 diff 视图，仅通过快照原文展示 |

**设计决策原因：** 一期团队规模小、Case 修改频率可控，完整版本管理会引入版本号、分支、回滚等复杂度，与一期的轻量定位不匹配。`case_snapshot` 机制已足够保障历史执行的可追溯性。二期可根据需求引入版本管理。

## 6. 场景管理

### 6.1 功能定位

**场景（Scene）** 是 DataForge 的高阶编排层，用于将多个已创建的 Case 按照指定的执行顺序和依赖关系组合成一个可重复执行的「数据准备流程」。

**典型使用场景：**

| 场景示例 | 说明 |
|----------|------|
| 电商全链路数据初始化 | 先执行「用户 Case」→ 再并行执行「商品 Case」和「地址 Case」→ 最后执行「订单 Case」 |
| 申报数据回归准备 | 按业务顺序依次初始化主体、申报期、申报明细三张表的数据 |
| 压测数据批量灌入 | 多个独立 Case 并行执行，最大化造数速度 |
| 每日环境重置 | 定义好一套场景，每天一键恢复测试环境干净数据 |

**场景与 Case 的关系：**

```
场景（Scene）
  └── 节点1：Case A（用户信息）    ──────────────────┐
  └── 节点2：Case B（商品信息）    ── 并行（无依赖） ──│── 节点4：Case D（订单）
  └── 节点3：Case C（地址信息）    ──────────────────┘
```

**一期功能边界 — 跨节点数据传递：**

一期场景管理**不支持**节点间的运行时数据传递（即节点 B 无法自动读取节点 A 刚插入的主键值作为外键）。

跨表外键关联的一致性**应在单个 Case 内通过字段关联机制解决**（见 4.4.6），而非依赖场景节点间传递。

**正确使用姿势说明：**

| 需求 | 推荐做法 |
|------|---------|
| 用户表 user_id 要与订单表 buyer_id 一致 | 在同一个 Case 内，将 user_info.id 关联到 order.buyer_id，一次执行完成 |
| 两批独立数据，无外键依赖 | 分别建两个 Case，在场景中编排顺序 |
| 场景节点 B 需要引用节点 A 的数据 | 一期不支持，二期通过「场景变量」机制规划支持 |

> **设计决策原因：** 运行时数据传递需要节点 A 完成后将主键列表写入共享存储，节点 B 读取后以 PICK_FROM_LIST 方式使用。该机制引入节点间的数据耦合，显著增加执行引擎复杂度和调试难度，且会使 Case 本身失去独立可复用性。一期明确不支持，二期可通过「场景输出变量 + 节点输入绑定」机制扩展。

```
└──────────────────────────────────────────────────┘
```

#### 6.4.3 执行逻辑

**拓扑分层执行（Kahn 算法）：**

```
1. 对场景 DAG 做拓扑排序，得到分层结果（每层内节点无依赖关系）
2. 逐层执行：
   a. 同一层内的所有节点并行提交（每个节点对应一个独立的 df_exec_task）
   b. 等待本层全部节点达到终态（成功 / 失败 / 跳过）
   c. 检查各节点的失败策略：
      - 若某节点失败且失败策略=「终止场景」→ 标记后续所有节点为「已取消」，停止执行
      - 若某节点失败且失败策略=「继续执行」→ 标记该节点为失败，继续下一层
   d. 进入下一层
3. 所有层执行完毕后，计算场景整体状态：
   - 全部节点成功 → 场景成功
   - 存在节点失败但未触发终止 → 场景部分成功
   - 触发终止策略 → 场景失败
```

**状态流转：**

```
场景节点状态：待执行 → 执行中 → 成功 / 失败 / 已取消（前置节点触发终止）
场景整体状态：待执行 → 执行中 → 成功 / 失败 / 部分成功
```

### 7.4 通用 UX 设计

- 每个工具卡片可展开/收起
- 所有工具结果区域均有「一键复制」按钮，复制成功后按钮变色 1.5 秒
- 生成历史保存到 localStorage，每个工具保留最近 5 次生成参数，支持一键回填
- 批量生成数量较多时（>1000条）展示进度条

**导出功能：**

| 触发条件 | 导出格式 | 说明 |
|---------|---------|------|
| 生成结果条数 ≥ 100 | CSV / TXT | 工具结果区下方展示「⬇️ 导出 CSV」和「⬇️ 导出 TXT」按钮 |
| 生成结果条数 < 100 | 不展示导出按钮 | 少量数据直接复制即可 |

- **CSV**：每行一条数据，列标题对应工具输出字段（如身份证工具：身份证号, 省份, 出生日期, 性别）
- **TXT**：每行一条数据，纯文本，适合直接粘贴到 SQL 或其他工具
- 导出时文件名格式：`dataforge_{工具名}_{yyyyMMddHHmmss}.{ext}`，如 `dataforge_idcard_20260708103000.csv`
- 导出在前端本地完成（Blob + a 标签），无需请求后端

**UPDATE 模式说明（一期不支持）：**

一期造数引擎仅支持 INSERT 模式，不支持 UPDATE 已有数据。对于「给已有数据打状态」的需求，建议通过以下方式处理：

- 在快捷工具中生成目标值列表后，手动执行 UPDATE SQL
- 或通过目标数据库的管理工具直接操作
- 二期可根据需求评估引入 UPDATE 模式（需要用户指定 WHERE 条件配置，复杂度较高）

#### 8.2.3 删除数据源规则

删除是高风险操作，需要明确级联行为：

**触发条件：** 点击操作列【删除】按钮

**删除前校验：**

| 检查项 | 存在时的处理方式 |
|--------|----------------|
| 该数据源下有**未删除的 Case** | **硬拦截**，弹窗提示「该数据源下还有 N 个 Case（xxx、xxx…），请先删除或迁移后再操作」，不允许继续删除 |
| 该数据源下有**正在执行的任务** | **硬拦截**，弹窗提示「该数据源下有 N 个任务正在执行，请等待执行完成或强制停止后再删除」 |
| 该数据源下所有 Case 均已逻辑删除，且无执行中任务 | 允许删除，进入二次确认弹窗 |

**二次确认弹窗内容：**

```
⚠️ 确认删除数据源「test_db」？

此操作将同时：
  • 删除该数据源的所有表结构缓存（df_table_cache / df_column_cache / df_index_cache）
  • 清除对应 Redis 缓存键
  • 历史执行记录中数据源名称将保留（冗余字段），不受影响

已逻辑删除的 Case 的历史执行记录仍可查看。
此操作不可恢复。

[取消]   [确认删除]
```

**删除后行为（后端）：**
1. 数据源记录软删除（`is_deleted=1`，或直接物理删除，以实现为准）
2. 清除 `df_table_cache` / `df_column_cache` / `df_index_cache` 中该数据源的所有缓存行
3. 清除 Redis 中 `df:tables:{datasource_id}`、`df:columns:{datasource_id}:*`、`df:indexes:{datasource_id}:*`
4. 移除动态连接池中该数据源的连接引擎（`DynamicConnectionPool.remove_engine(datasource_id)`）
5. 若该数据源是某用户的默认数据源，将对应用户的 `default_datasource_id` 置为 NULL

### 8.3 新增/编辑数据源表单

| 字段 | 类型 | 必填 | 校验规则 |
|------|------|------|----------|
| 数据源名称 | 文本 | ✓ | 1~50字，全局唯一，不含特殊字符 |
| 数据库类型 | 下拉（仅MySQL） | ✓ | — |
| Host | 文本 | ✓ | 合法 IP 或域名 |
| Port | 数字 | ✓ | 1~65535，默认 3306 |
| Database | 文本 | ✓ | 合法数据库名 |
| 用户名 | 文本 | ✓ | — |
| 密码 | 密码框 | ✓（新增必填，编辑不填则保持原密码） | — |
| 所属分组 | 下拉 | ✓ | 销项组 / 申报组 |
| 备注 | 文本区域 | 否 | ≤500字 |

**表单底部操作按钮：**
- [测试连接]：测试连通性，显示「连接成功，数据库版本：MySQL 8.0.x」或错误详情
- [取消] [保存]

**保存后自动触发：**
1. 加密密码（AES-256-CBC）存入 DB
2. 异步触发数据源初始化任务（Celery）
3. 页面显示「数据源已保存，正在后台初始化表结构，预计需要 10~60 秒...」

### 8.4 数据源初始化流程

```
触发条件：新增保存 / 编辑保存 / 手动点击[立即同步]
    │
    ▼
① 检查 Redis 分布式锁（dataforge:lock:sync:{datasource_id}）
   └── 已锁定 → 返回「同步任务正在进行中，请稍候」
    │
    ▼
② 获取锁，更新 datasource.status = 同步中
    │
    ▼
③ 连接目标数据源，执行 SHOW TABLES 获取所有表名
    │
    ▼
④ 批量查询 information_schema：
   - TABLES：表注释、行数估算、引擎、字符集等
   - COLUMNS：所有表的字段信息（类型、可空、主键、默认值、注释等）
   - STATISTICS：索引信息
    │
    ▼
⑤ 批量 UPSERT 写入本地 MySQL：
   df_table_cache / df_column_cache / df_index_cache
    │
    ▼
⑥ 刷新 Redis 缓存：
   - dataforge:tables:{datasource_id}
   - dataforge:columns:{datasource_id}:{table_name}（逐表写入）
    │
    ▼
⑦ 更新 datasource.status = 正常，last_sync_at = 当前时间
   释放分布式锁
```

### 8.5 定时同步任务

- **触发时间：** 每天凌晨 02:00（Celery Beat 调度）
- **范围：** 所有 status=正常 的数据源
- **策略：** 增量同步（对比 information_schema 与本地缓存的差异，仅更新变更内容）
- **通知：** 同步完成后在系统消息中推送摘要（新增 N 张表，更新 N 张表，删除 N 张表）

### 8.6 连接状态心跳检测

- Celery Beat 每 30 秒对所有数据源执行轻量 ping（`SELECT 1`）
- 结果写入 Redis：`dataforge:ds:status:{datasource_id}` TTL=60s
- 前端数据源列表和造数引擎顶部状态指示灯通过轮询接口获取（每 30 秒轮询一次）

### 9.1 性能要求

| 场景 | 性能目标 |
|------|----------|
| 表列表加载（缓存命中） | < 200ms |
| 字段配置页加载（缓存命中） | < 300ms |
| 数据源切换响应 | < 500ms |
| 造数总览页面加载 | < 1s |

| 普通接口响应时间 | P99 < 500ms |
| 场景执行调度延迟 | 层间切换延迟（等待上层完成→触发下层）< 2s |

### 9.2 可靠性要求

| 需求 | 说明 |
|------|------|
| 造数任务失败重试 | 单批次失败自动重试 3 次，指数退避 |
| 断点续传 | 任务中断后可从最后成功批次继续 |
| 数据一致性 | 批量 INSERT 使用事务，单批次原子性保证 |
| 缓存降级 | Redis 不可用时降级查本地 DB 缓存表 |
| 数据源连接池 | 每个数据源独立连接池，连接失败不影响其他数据源 |
| 场景节点隔离 | 单节点失败不影响其他并行节点，仅按失败策略决定是否终止 |

### 9.3 安全要求

| 需求 | 实现方案 |
|------|----------|
| 数据库密码加密存储 | AES-256-CBC，密钥存于环境变量 |
| 接口认证 | JWT Token，7天有效，支持主动失效（Redis 黑名单） |
| 数据权限 | 后端 SQL 自动注入 group_type 过滤，前端无法绕过 |
| 敏感操作审计 | 所有增删改执行操作写入 df_audit_log，不可删除 |
| SQL 注入防护 | 使用 SQLAlchemy ORM / 参数化查询，禁止字符串拼接 SQL |
| 数据源连接隔离 | 用户只能操作本组数据源，跨组拒绝 |
| XSS/CSRF 防护 | 前端 Vue 自动转义 + 后端 CORS 白名单 |
| **登录失败锁定** | **同一用户名连续登录失败 ≥ 5 次，锁定账号 10 分钟；锁定期间返回错误码 1005 并提示剩余锁定时间；计数存 Redis（`df:login:fail:{username}`，TTL=10min），锁定解除后自动清零** |

**登录失败锁定实现细节：**

```
用户提交登录
    │
    ▼
检查 Redis df:login:fail:{username} 是否存在且 >= 5
    ├── 是 → 返回 1005「操作过于频繁，账号已锁定，请 X 分钟后重试」（不查 DB）
    └── 否 → 继续校验密码
              │
              ├── 密码正确 → 删除失败计数 Key，正常登录
              └── 密码错误 → INCR df:login:fail:{username}（不存在则创建，TTL=600s）
                            → 若计数达到 5，返回「密码错误，账号已被锁定 10 分钟」
                            → 若计数 < 5，返回「密码错误，还剩 N 次尝试机会」
```

## 10. AI 预留接口规范（二期）

> 一期在造数引擎内预留标准化的外部调用接口，供二期 AI 智能造数模块接入，无需改造核心引擎。

### 10.1 设计原则

## 11. 消息通知中心

系统内置轻量消息中心，用于接收与造数业务相关的系统通知，无需依赖外部邮件或 IM 工具。消息只在系统内展示，不对外推送。

### 11.4 消息内容格式

每条消息包含以下字段：

**消息内容模板示例：**

```
  标题：数据源连接异常
```

### 11.6 消息存储与清理

**存储方案：** 消息存入数据库表 `df_notification`（见架构文档 DB 设计），不使用 WebSocket 推送，前端通过轮询获取未读数量。

**轮询策略：** 前端每 60 秒轮询一次未读数量接口（`GET /api/v1/notifications/unread-count`），收到数量变化时更新铃铛角标。

**消息保留策略：**

| 消息优先级 | 保留时长 |
|----------|---------|
| 🔴 高优先级 | 90 天 |
| 🟡 中优先级 | 30 天 |
| 🟢 普通 | 14 天 |

过期消息由 Celery Beat 每日凌晨 03:00 清理（软删除）。每用户最多保留 500 条，超出时按时间倒序保留最新的。

## 12. 业务错误码规范

### 12.1 设计原则

- 所有接口错误均通过统一响应格式返回（见架构文档 2.2.2）
- `code=0` 表示成功；`code` 非 0 表示失败
- 错误码按模块分段，前端可根据 `code` 精确展示错误提示，无需解析 `message`
- `message` 字段为中文可读文本，可直接展示给用户

### 12.2 错误码分段规则

| 段 | 范围 | 模块 |
|----|------|------|
| 通用错误 | 1000~1099 | 参数校验、认证、权限 |
| 用户模块 | 1100~1199 | 注册、登录、审批、权限管理 |
| 数据源模块 | 1200~1299 | 数据源 CRUD、连接测试、同步 |
| 造数引擎 | 1300~1399 | 字段配置、关联管理、执行任务 |
| Case 模块 | 1400~1499 | Case CRUD、执行、复制 |
| 场景模块 | 1500~1599 | 场景 CRUD、编排校验、执行 |
| 工具模块 | 1600~1699 | 各工具生成错误 |
| 系统级 | 9000~9099 | 服务内部错误、依赖不可用 |

### 12.4 前端错误处理规范

```typescript
// utils/request.ts — 响应拦截器错误处理
const ERROR_MESSAGE_MAP: Record<number, string> = {
  1001: '登录已过期，请重新登录',
  1002: '权限不足，请联系管理员',
  // ... 其他需要特殊处理的错误码
}

response.interceptors.response.use(
  res => res.data,
  error => {
    const code = error.response?.data?.code
    const message = ERROR_MESSAGE_MAP[code] ?? error.response?.data?.message ?? '网络请求失败'

    // 1001: 跳转登录页
    if (code === 1001 || code === 1006) {
      useAuthStore().logout()
      router.push('/login')
      return
    }

    window.$message.error(message)
    return Promise.reject(error)
  }
)
```
